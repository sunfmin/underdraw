
FORMAT — how to write a description
  The reference for writing screen.json, domain.json and tokens.json,
  from the files' keys to every built-in component.

FILES
  <dir>/screen.json   the screen: view model, fixtures, conditions, nodes
  domain.json         optional: the types, conditions, operations and
                      samples every screen of the project shares; its
                      directory is the
                      project root (DOMAIN.JSON below)
  components/<Name>.json
                      optional: a component every screen of the project
                      shares, at the project root (COMPONENTS below)
  tokens.json         design tokens; read by name, always this file name,
                      from the nearest directory at or above <dir> that
                      has one (beside screen.json, or shared above it)
  <dir>/platforms/<name>.json
                      how one platform builds it: `underdraw handoff --help`
  <dir>/journeys/<name>.json
                      optional: one path a person takes across screens,
                      walked by `check <root>` (JOURNEYS below)

SCREEN.JSON
  {
    "screen":     "TodoList",          the name code is generated under
    "title":      "My todos",          what a person calls it
    "locale":     "zh-CN",             optional BCP 47 tag: glyph forms, line breaks
    "tokens":     "tokens.json",
    "params":     ["orderId"],         what it is opened with: fields of data (PARAMS)
    "data":       {…}, "types": {…},   the view model
    "fixtures":   {…},                 sample view models, one state each
    "conditions": {…},                 every yes/no the screen decides, named
    "operations": {…},                 the queries and commands it calls (OPERATIONS, PAGING)
    "components": {"Name": component, …}
                                       the screen's own components, beside the
                                       project's components/ (COMPONENTS)
    "root":       node,                the screen once data has arrived
    "phases":     {"loading": node, "error": node}
                                       trees shown before data; they read no data
    "transitions": [{"from", "on", "outcome"?, "to"}, …]
                                       which state acting on a node leads to (TRANSITIONS)
  }
  "$comment", "$note", "$why" may be put on anything: read by people only.

DATA AND TYPES
  "data" names the roots a path may start from; "types" names every shape.
    "data":  { "todos": "Todo[] ..200", "summary": "Summary", "plan": "Plan" },
    "types": {
      "Todo":    { "id": "string", "title": "string 1..80", "done": "bool = false",
                   "due": { "type": "date?", "doc": "No due date when null" } },
      "Summary": { "remaining": { "type": "int 0..", "derived": { "app": "undone todos" } } },
      "Plan":    "enum(monthly, yearly)"
    }
  A field is   type range? default?   or {"type", "doc", "derived", "from", "view"}:
    type     a built-in, or a named type; "[]" after it: a list; "?": nullable
             ("date?", "Photo[]", "Photo[]?")
    range    lo..hi, either side open: a number's value, a string's length,
             a list's count ("int 1..16", "string ..200", "image[] 5..")
    default  "= <JSON>": what a fixture that leaves the field out holds
             ("bool = false", "string = \"\""). T? defaults to null. A list
             has no default: write [].
    doc      one line for the person and the implementing agent
    derived  who computes it, and how: {"app": "undone todos"} for what the
             app works out for the screen, {"server": "the person owns it"}
             for what the server answers with. Fixtures supply the value;
             the screen never computes: no arithmetic anywhere. No
             operation's result reaches an app-derived field, and view
             state is never derived by the server.
    from     on a field of "data" only: the query whose result fills it,
             or "<query>.<field>" for one field of that result (OPERATIONS).
             A field without it is the app's or the screen's.
    view     true: view state, held by the screen alone (an open menu, the
             row a popup is about), not domain data. No operation answers
             with it, so keep it out of the types operations return: wrap
             the domain type in a row type that adds it.
               "data":  { "docs": "DocRow[]",
                          "rowMenu": { "type": "RowMenu?", "view": true } },
               "types": { "DocRow": { "doc": "Doc",
                                      "menuOpen": { "type": "bool = false", "view": true } },
                          "Doc": { "id": "string", "title": "string 1..60" } }
  Built-ins, with how a fixture writes them:
    string "…"   int 3   number 4.92   bool true   date "2026-11-12"
    url "https://…"   image "photo-1.jpg"   icon "wifi" (a Material Symbols
    name; ".fill" for the solid form)   money {"amount": 18500, "currency": "JPY"}
  Named types start with a capital letter; every object and enum is named
  (no inline shapes). Only T? may be null.

FIXTURES
  Each is one whole value of "data", by name, in the order they are shown.
    "fixtures": {
      "default": { "todos": [{"id": "1", "title": "Milk", "done": true}],
                   "summary": {"remaining": 0}, "plan": "monthly" },
      "empty":   { "$patch": "default", "todos": [], "summary": {"remaining": 0} }
    }
  "$patch": "<fixture written above>" starts from it and deep-merges the rest
  over it: objects merge key by key; lists and scalars replace.
  {"$sample": "<name>"}, in place of any value in a fixture (the fixture
  itself, a field, an item), starts it from that sample in domain.json's
  "samples" (DOMAIN.JSON), so screens showing the same data (a tree's lines,
  two journeys) write it once; any other key beside "$sample" merges over
  it as "$patch" does (only over an object sample):
      "journeys": { "$sample": "twoJourneys" },
      "first":    { "$sample": "buy", "name": "Buy again" }
  It reads, checks and renders exactly as the value written out. A sample
  is checked where a fixture uses it, as that field's type: one of the
  wrong type is a finding at the field naming the sample ("… : the fixture
  starts it from sample buy"); a name no sample has is a finding too.
  A fixture may leave out only fields with a default; no unknown fields;
  types and ranges hold. Use real sample values. The first fixture is the default
  for `render`.

PARAMS
  What the screen is opened with: a list naming fields of "data".
    "params": ["orderId"],
    "data":   { "orderId": "string 1..", "order": {"type": "Order", "from": "getOrder"} }
  Every fixture gives each param itself, or through its "$patch", even one
  that is nullable or has a default. A param is not view state, not filled
  by a query ("from") and not derived: what opens the screen gives it.
  Each "navigate" to the screen gives each param, of its type, in "with",
  and nothing else; "params": [] says it is opened with nothing, so a
  navigate to it gives no "with". With no "params", nothing a navigate
  gives it is checked. `check <root>` holds every navigate to a screen
  under the root to its params; a navigate to a screen not drawn yet is
  an assumption, its "with" unchecked.

CONDITIONS
  Every decision is named once, and used by name:
    "conditions": {
      "hasTodos": { "when": "summary.total > 0", "label": "Has todos" },
      "allDone":  { "when": "hasTodos && summary.remaining == 0", "label": "All done" },
      "yearly":   { "when": "plan == \"yearly\"", "label": "Yearly plan" }
    }
  Grammar of "when":
    expr = and ("||" and)*        and = not ("&&" not)*
    not  = "!" not | compare      compare = atom (op atom)?
    op   = == != < <= > >=        atom = path | condition | literal | ( expr )
    literal = number | "string" | true | false | null
  - A condition is a Bool: no truthiness. Write != null, > 0, == "x".
  - == and != compare equal types; null compares only with a nullable value.
    < <= > >= compare numbers or dates. An enum compares with a member's
    name as a string.
  - A condition may use others by name; no cycles.
  - Every condition must be true in one fixture and false in another.
  A use site ("if", "disabled", a cases branch's "if") is only terms
  joined by &&, each !? <condition or Bool path>: "hasTodos", "!canAdd",
  "item.done", "walks && !picked". It holds when every term does, and a
  != null a condition in the chain makes reads the value under it, as in
  a condition's own && chain. || and comparisons are a named condition.
  A condition on a type is named <Type>.<name>, and its "when" reads the
  type's own fields, never the screen's data:
    "Order.cancellable": { "when": "status == \"pending\"", "label": "Not shipped yet" }
  A value of the type reads it as a Bool field, wherever the value is: a
  use site ("if": "item.cancellable"), a placeholder ({item.cancellable}),
  or a condition of the screen ("order != null && order.cancellable").
  Inside one on a type, another of that type is named short ("cancellable
  && !hasNote" in Order.quiet); a condition over the screen's data is not
  named there at all, and one on a type is never named whole elsewhere.
  It is no field: fixtures never give it, the type has no field of its
  name, and it is used only through a value of its type (check names one
  used on a value of another type). A screen that reads it must hold, in
  its fixtures, one value of the type it is true of and one it is false
  of; a screen that never reads it is not held to it.
  Declare one in domain.json (DOMAIN.JSON) to share it: the domain has no
  screen's data, so a condition every screen asks of an Order is one on
  Order. A condition over a screen's data stays that screen's.

TEMPLATES AND FORMATS
  Any string may hold placeholders: {path} or {path|format}. A path is
  dot-separated: a data root, or inside "item" also item, index and the
  index a repeat around it names ("index": "row"). No operators in a
  placeholder. {{ and }} are literal braces.
    "text": "{summary.remaining} left · {booking.total|money}"
  Formats (closed set; a value that needs one and lacks it is a fault):
    (none)       string, int
    money        money             ¥18,500, per the locale
    date         date              medium date
    date:short   date              short date
    number:N     number or int     exactly N decimals
    number:N-M   number or int     N to M decimals
    count        list              its length
  Text properties — text, title, subtitle, label, detail — always get text.
  Any other property given exactly one placeholder and nothing else gets the
  value itself, with its type: "value": "{listing.rating}", "each" items.
  A bool, enum, image or object cannot be shown as text: choose words with
  cases. A nullable value (or one reached through it) may be shown, or given
  to a param that is not nullable, only where its own or an enclosing "if"
  or cases branch tests it != null, directly or via a condition whose
  top-level && chain says so. A negation guarantees nothing.

CASES
  Any property's value can be chosen per state; the first true branch wins,
  and the last branch must be "else":
    "leadingIcon": { "cases": [ { "if": "item.done", "then": "check_circle.fill" },
                                { "else": "circle" } ] }
  A slot (children, leading, …) is not a property: it holds nodes, never
  cases. To show one node or another, write both, each with its own "if".

NODES
  A node is an object:
    "id"        unique in every state: "todo-{index}" inside an item
                template, "cell-{row}-{index}" inside one inside another
                ("index" below); check names an id two nodes share. Required on
                a node with "on", "bind" or "assumed", and on an instance
                of a component holding one; any other may leave it out
                and is given one, the same on every run and unchanged by
                an unrelated node added: the id of the node it is in, its
                component in kebab case, and the first three words of its
                text, title, label or icon ("page-text-hello-name" for
                {"component": "Text", "text": "Hello {name}"} in "page";
                four hex digits for text with no ASCII word), "-{index}"
                after an item's (inside a repeat inside one, the outer's
                {index} in the id it is in said by the outer's "index"
                name), "-2", "-3"… after one taken. A component's
                own nodes are given theirs without its root's. check,
                render, handoff and the gallery all name it so
    "component" what the node is: a built-in component (BUILT-IN COMPONENTS)
                or one of the screen's own (COMPONENTS); check refuses
                "kind", its old name
    "if"        a use site: the node and all inside it show only when it holds
    "only"      "compact" or "regular": shown at that breakpoint only
    "each"      a list path: repeat "item" once per element
    "item"      the node repeated; it sees item (the element) and index (0..)
    "index"     a name for this repeat's index, beside "each": "row". A
                repeat inside one rebinds item and index, so a node there
                reaches this one's index only by its name:
                  { "id": "rows", "component": "List", "each": "rows", "index": "row",
                    "item": { "id": "row-{index}", "component": "List", "each": "item.cells",
                      "item": { "id": "cell-{row}-{index}", "component": "Button", … } } }
                gives cell-0-0, cell-0-1, cell-1-0…; a transition or a
                journey names it as written, "cell-{row}-{index}.tap". A
                word no data root, enclosing repeat, item, index or n takes
    "limit"     at most this many elements: 5, or {"compact": 6, "regular": 9}
    "nest", "fold", "indent"
                beside "each": its rows are a tree (TREES below)
    "bind"      a path (or a list of paths) the person edits; its value is
                given to the component as "value" ("bind": "composer.text";
                a date range: ["booking.checkIn", "booking.checkOut"])
    "disabled"  a use site: "!canAdd"
    "on"        actions (ACTIONS below)
    "with"      the params of a screen's component, one value each (COMPONENTS)
    "assumed"   what you guessed there and what else it could be, in a
                sentence (ASSUMED below): drawn orange until the person agrees
    "platform"  {"web": {"hidden": true, "$why": "…"}} or {"ios": {"<prop>": v}}:
                one platform leaves it out, or builds a prop differently
    any other key   a prop of the component, such as "text", "variant", "icon"
  Slots hold child nodes (one node or a list; never cases: use "if"):
    children   the body, in order
    leading    before the body;  trailing  pushed to the far end
               (in a Grid or Columns these two do not fill its cells in
               turn: give the cells as children, in order)
    action     in the body after children (EmptyState's button)
    overlay    floats over the node; its "anchor" is "bottom-trailing"
               (default), "top-leading", "top-trailing", "bottom-leading"
               (16 in from the corner), "center" (the middle of the node:
               a dialog) or "bottom" (flush along the bottom edge, as wide
               as the node: a sheet)
    foot       stays at the foot of the node while what is above it scrolls,
               out of its siblings' order: a chat's box to write in, a side
               panel's buttons. Drawn after everything else, on the bottom
               edge of a column (Stack, Card): a pane in a Columns is as
               tall as its row. `compare` treats it as pinned. StickyBar
               does this for a whole screen:
               { "id": "side", "component": "Stack", "children": [ …cards ],
                 "foot": { "id": "composer", "component": "Row", … } }
  A component draws its slots only if its look places "$children"; check
  refuses a node in a slot of one whose look does not (IconButton, Badge).
  "each" with no "item" passes the elements to the component as "items" (photos):
    { "id": "photos", "component": "ImageCarousel", "each": "listing.photos" }
  "item" sees item and index; "children" of the same node are drawn once
  and see neither.

TREES
  A hierarchy (a file tree, nested comments, categories) is one list whose
  elements hold a list of their own type, never a flat list with a depth
  number. Beside "each", "nest" names that field: each row is followed by
  its own rows, one level further in, at any depth. "indent" is how far in
  each level is drawn, written once here (a space token or points; 16 when
  left out): every row under the tree follows it, whatever component draws
  it, so no look pads by depth. "fold" names a bool field of the row in
  view state: while it is true the row's own rows are not drawn. A fixture
  folds a row by setting it, and lists every row still; a node toggles it.
    "types": { "Entry": { "name": "string 1..", "children": "Entry[]",
                          "folded": { "type": "bool = false", "view": true } } },
    "fixtures": { "default": { "files": [
        { "name": "src/", "children": [
            { "name": "main.rs", "children": [] },
            { "name": "lib/", "folded": true, "children": [
                { "name": "a.rs", "children": [] } ] } ] },
        { "name": "README.md", "children": [] } ] } },
    { "id": "files", "component": "List", "each": "files",
      "nest": "children", "fold": "folded", "indent": "space.4",
      "item": { "id": "file-{index}", "component": "Row", "children": [
        { "id": "file-{index}-fold", "component": "IconButton", "icon": "chevron_right",
          "on": { "tap": { "toggle": "item.folded" } } },
        { "id": "file-{index}-name", "component": "Text", "text": "{item.name}" } ] } }
  draws src/, main.rs and lib/ one step in, and README.md; a.rs is not
  drawn, as lib/ is folded. "index" counts every row in that order, folded
  away or not (a.rs is file-3, README.md file-4), so a row's id stays the
  same whatever is folded above it. Rows of different kinds share the tree
  by one row type: give it a field per kind and "if" each node in "item".
  "limit" counts only the rows at the top. check names a "nest" that is not
  a list of the element's own type, a "fold" that is not a bool in view
  state, and either one, or "indent", without "nest".

ASSUMED
  "assumed" marks a node as a guess the person has not confirmed. They
  answer it in the gallery: right, or wrong and what is right instead. To
  answer, they need what was guessed and what else it could be, so say
  both, in a whole sentence:
    "assumed": "Card fields are drawn here; the real build may use the payment provider's hosted fields"
  check refuses one too short to say that: empty, or a word or two (fewer
  than 5 words, or than 10 characters in Chinese or Japanese). Write it in
  the language you speak with the person, whatever the description's
  "locale" is. Take it out once the person confirms it.
  The assumptions underdraw makes itself, a navigate to a screen not drawn
  yet and a component it does not know, come as whole sentences naming
  that screen or component, in English, Chinese or Japanese as the command that reports
  them is asked: --lang en|zh|ja on `check <root>`, `render` and
  `gallery`, English by default, whatever the machine's locale.

LAYOUT ON A NODE
  Direction comes from the component: Stack, List, Scroll, Screen, Card,
  FieldGroup are columns; Row, NavBar, StickyBar, Carousel are rows; Grid
  and Columns are grids. These containers take from the node:
    "gap"        a length: 12 or a token "space.3"
    "padding"    a length, [vertical, horizontal] or [top, right, bottom, left]
    "radius"     a length or "radius.md"; also clips the children
    "border"     a colour token: "color.border"
    "elevation"  an elevation token: outlined in the wireframe
    "columns"    Grid and Columns only: a count, or tracks ["58%", "1fr"]
    "dividers"   Grid and Columns only: true draws a line between the cells,
                 in the line ink, for panes split without a border round each
  Each cell of a Grid or Columns is as tall as its row, so its border and
  fill reach the row's foot.
  Section takes "gap" and "padding" too. Width, grow, alignment and sizes
  are never written on a node: they belong to a component's look (LOOKS).
  When a built-in component does not lay out as needed, define one.

ACTIONS
  "on" maps an event (usually "tap") to actions, each "name": argument.
  What reads or changes domain data is an operation, called with "call"
  (OPERATIONS below): saving, deleting, sending a form, loading again
  (a retry button), choosing what the server keeps (a delivery option, a
  filter it applies), marking a todo done. Everything else is UI-only,
  what the screen does by itself, and is one of these:
    navigate   go to a screen    "navigate": "Checkout", "with": {"id": "{listing.id}"}
                                 "with" gives each of its params (PARAMS)
    back       go back           "back": true
    open       show a popup      "open": "cancel-dialog", "with": {"id": "{item.id}"}
    close      hide it           "close": "cancel-dialog"
    scrollTo   scroll to a node  "scrollTo": "calendar"
    share      the system sheet  "share": "{listing.url}"
    copy       a screen's link   "copy": "Document", "with": {"id": "{item.doc.id}"}
    set        write view state  "set": "item.selected", "to": true
                                 "set": {"booking.checkIn": null, "booking.checkOut": null}
    toggle     flip view state   "toggle": "sort.menuOpen"
  set and toggle write only view state: a field marked "view": true, or
  one inside such a field (DATA AND TYPES), an element of a view-state
  list included. check refuses any other action name, and set or toggle
  on domain data: "toggle": "item.done" on a Todo is "call": "toggleTodo".
  Each platform file says how to do each action it uses, "call" once.
  "with" is passed along with the action. A handler may be cases:
    "on": { "tap": { "cases": [ { "if": "!hasDates", "then": {"scrollTo": "calendar"} },
                                { "else": {"navigate": "Checkout"} } ] } }
  Event names, unlike action names, are free: "tap", or "change" on a node
  with "bind", raised once the person has edited the bound value. Its
  handler reads the new value through the bound path, so an edit that
  changes domain data calls the operation that saves it:
    { "id": "qty-{index}", "component": "Stepper", "bind": "item.quantity",
      "on": { "change": { "call": "setQuantity",
                          "with": { "id": "{item.id}", "quantity": "{item.quantity}" } } } }
  A node with "on" or "bind" is one a person can act on.

OPERATIONS
  The queries and commands behind the screen, declared once and called by
  name. Each is a query (it only reads) or a command (it changes something):
    "operations": {
      "listDocs":  { "query": "The team's documents, in the order sort names",
                     "params": { "sort": "SortKey = \"updated\"" },
                     "result": "Doc[] ..50" },
      "deleteDoc": { "command": "Deletes a document for everyone",
                     "params": { "id": "string" }, "requires": "canDelete",
                     "fails": { "notFound": "the document is already gone" } }
    }
    "query" or "command"   exactly one: what it does, in one line
    "params"   fields as in "data" (DATA AND TYPES); a named type is in "types"
    "result"   what it answers with: one of "types", written as a field type
               ("Doc", "Doc[] ..50", "Doc?"); never a built-in, and holding no
               view state. A query needs one; a command may have none.
    "requires" a condition (CONDITIONS) that must hold before it is called:
               the screen's, or one on a type ("Order.cancellable")
    "destructive"  true: a command that cannot be undone (deleting, sending,
               paying). Only its confirmation may call it (below), and its
               CLI command does nothing without --yes (`underdraw cli --help`)
    "bulk"     the name of its bulk form, which does it to many items at
               once: "bulk": "deleteDocs" (below). Only a command has one.
    "long"     true: a command that takes long (an export, an import). It
               answers with a job, and what reads the job is derived (below)
    "fails"    each way it can fail: a name and when, {"offline": "…"}
    "pages"    "cursor", for a query that answers one page at a time (PAGING)
  A query fills the fields of "data" that name it with "from":
    "data":  { "docs": { "type": "DocRow[] ..50", "from": "listDocs" } },
    "types": { "DocRow": { "doc": "Doc",
                           "menuOpen": { "type": "bool = false", "view": true } } }
  The field is of the query's result type, or of a type that wraps it: one
  field of the result's type (here doc), beside only view state and fields
  the app derives. "[]" and "?" match the result's. A command fills no field.
  "from": "<query>.<field>" fills it with one field of the result instead,
  of that field's type or wrapping it: "from": "listDocs.next".
  A parameter with a fixed set of choices is an enum in "types", and the
  view model offers the same enum, so a call passes one of them on:
    "types": { "SortKey": "enum(updated, created, title, owner)",
               "SortOption": { "id": "SortKey", "label": "string 1..8" } }
    "params": { "sort": "SortKey = \"updated\"" }   default: the one the screen selects
  The default is one of the choices; "with" gives a SortKey path
  ("{item.id}") or a member as a literal ("title"), and check refuses
  anything else.
  A node calls one as an action:
    "on": { "tap": { "call": "deleteDoc", "with": { "id": "{item.doc.id}" } } }
  "with" gives every parameter but those with a default, and no other. Each
  value is a template whose type is the parameter's: "{item.doc.id}" for a
  string; a nullable value only for a nullable parameter; words around a
  placeholder make a string. A literal works too: "title", 3, true, null.
  Its range lies inside the parameter's wherever the node can call it: a
  string's length, a number's value. A value of "string ..20" is not one
  of "string 1..20", since it may be "". Gate the node by a condition
  that narrows it, "disabled": "!hasCode" with "hasCode" when
  "code != \"\""; a condition's && chain narrows a value by != "" (at
  least one long), == a literal, and <, <=, >, >= a number. check refuses
  a call whose value may fall outside.
  A node that calls an operation with "requires" is gated by that
  condition, or one whose && chain names it: "disabled": "!canDelete" on
  the node, or "if": "canDelete" on it or around it (a handler's cases
  branch counts). check refuses a call that is not. One that requires a
  condition on a type is gated through a value of that type, the one it
  acts on: "if": "item.cancellable" on a row that calls cancelOrder with
  { "id": "{item.id}" }, or "disabled": "!item.cancellable".
  A destructive operation is called only from inside its confirmation: a
  popup (POPUPS) whose component's look has "backdrop": true, and that a node
  opens by its id with { "open": "<id>" }. The node a person first acts on
  opens it; only the button inside the popup calls the operation:
    the row menu's item:  "on": { "tap": { "open": "confirm-delete",
                                           "with": { "id": "{item.doc.id}" } } }
    the screen's overlay: { "id": "confirm-delete", "component": "Dialog",
                            "if": "confirmingDelete", "anchor": "center",
                            "children": [ …the question…,
      { "id": "confirm-delete-cancel", "component": "Button", "text": "取消",
        "on": { "tap": { "close": "confirm-delete" } } },
      { "id": "confirm-delete-confirm", "component": "Button", "text": "删除",
        "on": { "tap": { "call": "deleteDoc", "with": { "id": "{rowMenu.docId}" } } } } ] }
  with "confirmingDelete": "canDelete && rowMenu.confirming" in conditions,
  so the popup's "if" gates the call too, and a fixture that opens it.
  check refuses a call to a destructive operation anywhere else, a menu
  without a backdrop included.
  A command marked "bulk" derives a second operation, its bulk form, to
  act on many items the person has picked (a multi-selection):
    "deleteDoc": { "command": "Deletes a document for everyone",
                   "params": { "id": "string" }, "requires": "canDelete",
                   "destructive": true, "bulk": "deleteDocs",
                   "fails": { "notFound": "the document is already gone" } }
  derives deleteDocs, written nowhere and called by that name:
    params     the first parameter (the key: each item is one value of
               it) made a list of at least one, named with an s: "ids",
               string[] 1..; every other parameter as it is, the same for
               every item. The key has no default and is no list.
    result     one entry per item, in the order given: the item's key, and
               "error" for one not done (`underdraw cli --help`)
    requires   held item by item: an item it does not hold for is refused,
               and the others are still tried
    fails      each item's: one failing leaves the others to be done
    destructive  as the operation's: a bulk delete is confirmed too
  The screen holds the selection as view state, null while nothing is
  picked, its list at least one long:
    "data":  { "selection": { "type": "Selection?", "view": true } },
    "types": { "Selection": { "ids": "string[] 1..50",
                              "count": { "type": "int 1..",
                                         "derived": { "app": "ids' length" } },
                              "confirming": "bool = false" } },
    "conditions": { "hasSelection": { "when": "selection != null", … },
                    "confirmingDeleteSelected":
                      { "when": "hasSelection && selection.confirming", … } }
  A row's checkbox toggles a view-state field of its row ("toggle":
  "item.selected"), and the app keeps selection in step. The node that
  acts on the selection is gated on it, here opening the confirmation:
    { "id": "delete-selected", "component": "Button", "text": "删除所选",
      "disabled": "!hasSelection",
      "on": { "tap": { "open": "confirm-delete-selected" } } }
  and the confirmation's button, under "if": "confirmingDeleteSelected",
  calls the bulk form with the selection:
      "on": { "tap": { "call": "deleteDocs",
                       "with": { "ids": "{selection.ids}" } } }
  check refuses a call to a bulk form that is not given the selection (one
  path to a list in view state), or that is not gated on a non-empty one:
  its list may be empty, or the selection may be null where the node is
  (no "if" or "disabled" whose condition tests it != null). The bulk form's
  "requires" does not gate the node: no condition can say it of each item.
  Give the screen fixtures with none, some and all of the items picked.
  A long command has no bulk form: it answers with one job, not one per item.
  A long command ("long": true) answers with a job at once, and the job
  runs on. Two things are derived from it, so neither is written by hand
  (check refuses a type or an operation of either name):
    the job's type, its name and Job:  "ExportDocsJob": {
        "id": "string", "status": "JobStatus", "progress": "int 0..100",
        "result": "Archive?",   what the command answers with, once done
                                (left out when it answers with nothing)
        "error": "string?" }    which of its "fails" it ended in, once failed
      with "JobStatus": "enum(running, done, failed)", one for every job;
    the query that reads it, its name and Job:  "exportDocsJob":
      { "query": "Reads the job exportDocs started…", "params": { "id": "string" },
        "result": "ExportDocsJob", "fails": { "notFound": "no job has this id" } }
  The screen shows the job through the view model, as anything else: a
  field of "data" holds it, conditions read its status, and fixtures show
  it running, done and failed (check requires all three):
    "operations": { "exportDocs": { "command": "Exports every document…",
                    "result": "Archive", "long": true,
                    "fails": { "tooLarge": "over 2 GB" } } },
    "data":       { …, "job": "ExportDocsJob?" },      null before it is started
    "conditions": { "exporting": { "when": "job != null && job.status == \"running\"", … },
                    "exported":  { "when": "job != null && job.status == \"done\"
                                            && job.result != null", … },
                    "exportFailed": { "when": "job != null && job.status == \"failed\"", … } },
    "fixtures":   { …, "running": { "$patch": "default",
                                    "job": { "id": "j42", "status": "running", "progress": 40 } },
                    "done":   { …, "status": "done", "progress": 100, "result": {…} },
                    "failed": { …, "status": "failed", "progress": 65, "error": "tooLarge" } }
  A node shows the progress with "{job.progress}" under "if": "exporting".
  A done job holds its result; a failed one names one of the command's
  "fails". Loading and error stay phases: they come before the view model
  exists, and a job's running and failing happen inside it.
  Operations live in screen.json, one screen's own, and are not shared
  with other screens.

PAGING
  A query that answers one page at a time says so, and its result is one
  page: a type holding exactly one list, the page's rows, with the most a
  page holds ("..50"), and "next": "string?", where the next page starts,
  null on the last page.
    "operations": { "listDocs": { "query": "The team's documents",
                                  "pages": "cursor", "result": "DocPage" } },
    "types": { "DocPage": { "docs": "Doc[] ..50", "next": "string?" } },
    "data":  { "docs": { "type": "DocRow[]", "from": "listDocs.docs" },
               "next": { "type": "string?", "from": "listDocs.next" } },
    "conditions": { "hasMore": { "when": "next != null", "label": "More to load" } }
  "pages" adds two parameters, never written in "params": "cursor"
  (string?, where the page starts) and "limit" (int 1..50 = 50: as many
  rows as the page's list may hold). Every call to the query gives cursor:
  null for the first page (a sort, a retry), or the field of "data" filled
  from its "next" for the page after it, offered only while that is not
  null ("load more", or the end of a list):
    { "id": "load-more", "component": "Button", "if": "hasMore", "text": "Load more",
      "on": { "tap": { "call": "listDocs", "with": { "cursor": "{next}" } } } }
  Give the fixtures both states: one with "next" set (more to come) and one
  with it null (the last page), so hasMore holds in one and not another.
  check refuses a paged query whose result has no "next", a call that
  gives no cursor or another value, and a load more not gated by a
  condition that tests next != null. `underdraw cli` gives the query
  --cursor and --limit, and its stdout holds "next" (see cli --help).

COMPONENTS
  "components" holds the screen's own components, each by its name. A
  component's body is one of two, never both; check refuses a component
  with both, or with neither:
    a look     drawn as one element, and built by a platform as one:
                 "Chip": { "params": { "selected": "bool", "text": "string" }, "look": … }
               (LOOKS below). A node is one by its name, and gives it each
               param as a prop: { "id": "chip-direct", "component": "Chip",
               "text": "Direct", "selected": "{filters.direct}" }.
    nodes      a subtree written once and used more than once, with the
               params it reads, given in "with" (below).
  Either body declares its params one way: typed, as fields of data
  (DATA AND TYPES), { "selected": "bool", "count": "int = 0" }. A look's
  may instead be a list of the names, ["selected", "text"], each then
  taking any value. A typed prop is held to its type, as a param in
  "with" is: check refuses one missing (unless it has a default or is
  nullable) and one ill-typed, at "<id>.<prop>". A bool prop, typed or
  listed, may be given a condition of the screen's, "{hasDates}", and
  holds where it does, in render and the gallery; anything more ("!a",
  "a && b") is a condition of its own, named in "conditions".
  A look component declares in "params" every name its look reads, and its
  look reads nothing else: the first step of each placeholder ("{text}",
  "{label.short}" reads label), each name in an "if" or a branch of
  "cases", and, for a box with "frame": true, padding, gap, radius, border
  and elevation. What a repeat binds (n, index, item) is no param. check
  names each name a look reads that its params leave out, at
  "components.<Name>.look", and refuses "params" that is neither a list
  of names nor an object of types.
  underdraw's own components (BUILT-IN COMPONENTS) are look components of
  the same form; a screen's own of the same name replaces one whole.
  There is no kinds.json: check refuses one left beside screen.json. Move
  each of its components into "components", with the params its look
  reads, and delete the file.

  A component whose body is nodes is a piece of the screen used more than
  once (a nav bar, an order row with its cancel button), named with a
  capital and not as one of underdraw's own:
    "components": { "OrderRow": {
      "params": { "order": "Order", "menuOpen": "bool" },
      "nodes": { "component": "Card", "on": { "tap": { "navigate": "OrderDetail", "with": { "id": "{order.id}" } } },
                 "children": [
        { "id": "title",  "component": "Text", "text": "#{order.number}" },
        { "id": "cancel", "component": "IconButton", "icon": "cancel", "if": "order.cancellable",
          "on": { "tap": { "open": "cancel-dialog" } } },
        { "id": "more",   "component": "IconButton", "icon": "more_vert", "on": { "tap": { "toggle": "menuOpen" } } },
        { "slot": "children" } ] } } }
  and used where a node goes, phases included, by its name:
    { "id": "order-{index}", "component": "OrderRow",
      "with": { "order": "{item}", "menuOpen": "{rowMenuOpen}" },
      "children": { "id": "order-{index}-note", "component": "Text", "text": "{item.note}" } }
  - params: what it reads, typed as fields of data (DATA AND TYPES). It
    reads nothing else: a path that reaches past them, or a condition of
    the screen's, is refused. Each is given in "with", of its type, unless
    it has a default ("bool = false") or is nullable; check refuses one
    missing, one ill-typed and one it does not declare.
  - "with" gives each a template read where the instance is: "{item}" for a
    value, "#{item.number}" for text, a literal; a bool param may be given
    a condition of the screen's, "{hasDates}", and holds where it does.
  - nodes: one node, the root of its subtree. The root has no id: it is
    named by the instance's. Every node inside is named by the instance's
    id joined to its own: "cancel" in "order-3" is "order-3-cancel", and
    in states, handoff, captures, transitions and notes it is
    "order-{index}-cancel" as written. An id inside need only be unique in
    the component.
  - It holds no view state: check refuses a param marked "view". A flag
    such as a menu's open state is the screen's, in data marked "view":
    true, passed in whole ("{rowMenuOpen}"); a "set" or "toggle" on the
    param acts on what was passed, and check refuses it where a screen
    passes domain data. Shown on its own, a shared component holds its
    params itself, so its set and toggle on them are checked as view
    state's.
  - It varies only through its params and slots: the instance holds only
    id, component, with, if, only, assumed and the slots it fills; any
    other key reaches inside, and is refused. { "slot": "children" } in
    its nodes stands for what an instance gives in that slot (children,
    leading, trailing, action, overlay or foot): the screen's own nodes, read
    where the instance is, under their own ids. check refuses a slot the
    component places nowhere.
  - A component may use another; check refuses one that uses itself, at
    any depth: a node of OrderRow that is an OrderRow, or a look that
    nests the component it draws.
  - check refuses "ref", the old way to repeat a node: use the component.

  A component used by many screens is the project's: written once in
  components/<Name>.json at the project root (the directory holding
  domain.json; FILES), its file holding what "components" would hold
  under its name, either body:
    components/OrderRow.json     { "params": { "order": "Order" }, "nodes": { … } }
    components/OrderStatus.json  { "params": ["status"], "look": { … } }
  Every screen of the project uses it by name as if it declared it in its
  own "components": the domain's types type its params, and its nodes call
  the domain's operations, so the same OrderRow, cancel button and all, is
  on the order list and on one order's page, and an edit to the file
  changes both. Shared components may use each other and underdraw's; one
  that uses a screen's own is defined only on the screens declaring it,
  so share that one too.
  A screen may add its own beside them, never one of a name the project
  shares: check names the screen's at "components.<Name>", says it shadows
  the project's, and uses the project's in its place. A finding inside a
  shared component is at "components/<Name>.json …" and fixed in the file;
  a node inside it is named as any instance's (summary-cancel), and the
  gallery's ⌘C names it "at /nodes/… in components/<Name>.json".

  A shared component is shown on its own, so it can be discussed without
  a screen: its file carries "fixtures", each a value of its params, as a
  screen's carry values of its data ($patch included):
    components/OrderRow.json     "fixtures": { "pending": { "order": { "id": "A12", … } },
                                               "shipped": { "$patch": "pending", "order": { "status": "shipped" } } }
    components/OrderStatus.json  "fixtures": { "pending": { "status": "pending" } }
  Each fixture gives every param, of its type, and nothing else: a look's
  params, listed, take text, a number or true or false, the type the
  first fixture to give one gives. The description that shows it is
  components/<Name> (no file to write: the directory holds only its
  notes.json): `underdraw check <root>/components/OrderRow` checks the
  fixtures, a finding at "fixtures.<name>…", and `check <root>` and the
  gallery list it among the descriptions. It is one instance, named as
  the component is in kebab case (order-row, so its nodes are
  order-row-cancel), drawn in each fixture; it declares no screen, so no
  navigate reaches it. One that declares no params has one state to
  show and needs no "fixtures": without them it is drawn in one, named
  default. One with params and no fixtures is a finding there, never on
  a screen using it; a screen's own component takes none.

POPUPS
  underdraw has no dialog, sheet or menu component. A popup is a state like any
  other: a nullable field holds what it shows, a condition says it is open,
  a fixture opens it, and its node floats in the screen's "overlay":
    "data":       { …, "cancelling": "CancelRequest?" },
    "conditions": { "dialogOpen": { "when": "cancelling != null", "label": "Dialog open" } },
    "fixtures":   { …, "cancel-dialog": { "$patch": "default", "cancelling": {…} } },
    "root": { "id": "screen", "component": "Screen", "children": [ … ],
              "overlay": { "id": "cancel-dialog", "component": "Dialog", "if": "dialogOpen",
                           "anchor": "center", "children": [ … ] } }
  Inside it, paths through the nullable field are safe: "if" tests it.
  The button that opens it says so with a UI-only action, { "open": "cancel-dialog" };
  a list of choices inside it is "each" like anywhere else.
  "Dialog" is the screen's own component (COMPONENTS): "params": ["width"]
  and a look such as
  { "box": "column", "backdrop": true, "width": "{width|or:88%}",
    "padding": 24, "radius": 16, "fill": "paper", "stroke": "line",
    "children": ["$children"] }, with
  "width": {"compact": "88%", "regular": 480} on the node.
  - "anchor" places it: "center" for a dialog, "bottom" for a sheet. On a
    Screen, the middle and the bottom are those of the whole page, which
    is as tall as its content. A sheet's look leaves out "width".
  - The page is only as tall as its content: an overlay taller than that
    runs off it and is cut. check finds it, in each state at each of the
    project's widths (TOKENS.JSON); give the fixture that opens it more
    content behind it.
  - "backdrop": true dims the screen behind it; what is behind gets no
    number, since nothing there can be acted on while it is open.

PHASES
  "phases": { "loading": { "id": "loading", "component": "Screen", "children": [
                { "id": "sk", "component": "Skeleton", "shape": ["image 4:3", "line 60%"] } ] } }
  A phase tree has no data roots: no paths, no conditions on data. Inside
  root, every non-nullable path has a value. A section that loads on its own
  later is a nullable field and a condition, not a phase.

TRANSITIONS
  Which state a person reaches when they act on a node in another state.
  They are for the gallery, to lay the states out and click through them;
  they are not handed off, and need not name every event.
    "transitions": [
      { "from": "default",       "on": "order-{index}-cancel.tap",            "to": "cancel-dialog" },
      { "from": "cancel-dialog", "on": "cd-keep.tap",                         "to": "default" },
      { "from": "cancel-ready",  "on": "cd-confirm.tap", "outcome": "ok",      "to": "default" },
      { "from": "cancel-ready",  "on": "cd-confirm.tap", "outcome": "shipped", "to": "cancel-ready" }
    ]
    "from", "to"  a state: a fixture or a phase
    "on"          "<node id>.<event>": the node's "id" as written (a template
                  inside an item, "order-{index}-cancel"), and an event its
                  "on" handles. The node is shown in "from", at either
                  breakpoint.
    "outcome"     given exactly when the event calls an operation: "ok", or
                  one of the operation's "fails"
  Opening and closing a popup are transitions like any other. An event
  that navigates or goes back leaves the screen: it is not a transition.
  check names a transition whose state, node, event or outcome is not one.

JOURNEYS
  One named, linear path a person takes across screens, told as steps,
  each a state of one screen; a branch is another journey. One file each,
  <dir>/journeys/<name>.json, under any directory of the project:
    {
      "$comment": "The person opens an order and cancels it before it ships.",
      "steps": [
        { "screen": "Orders", "state": "default", "on": "order-{index}.tap" },
        { "screen": "Order",  "state": "open",    "on": "cancel.tap", "outcome": "ok" },
        { "screen": "Order",  "state": "cancelled" }
      ]
    }
    "screen"   the screen's name, as a navigate names it: "Orders"; or its
               directory, by its path from the project root (the nearest
               directory at or above <dir> holding domain.json; with none,
               <dir> itself): "orders/list". A name no description under
               the root declares is a finding at the step
    "state"    a fixture or a phase of that screen
    "on"       on every step but the last: "<node id>.<event>", the node
               acted on, its id as written, as in TRANSITIONS
    "outcome"  for an event that calls an operation: "ok", or one of its
               "fails"; which transition it takes
  It must be walkable: each "on" names a node its step's state shows (at
  either breakpoint) and an event it handles there, and that act leads to
  the next step: on the same screen, by a transition from this state on
  that event (with that outcome, when given) to the next step's state; on
  another screen, by a "navigate" to the screen the next step names. Data
  carries across screens: the values that navigate's "with" computes in
  its step's state are exactly the params the next step's fixture holds
  (PARAMS); a param that differs is named with both values. Steps on one
  screen are not held to each other. check
  <root> walks every journey under the root and names a broken one with
  the step that breaks ("steps.1.on"), so a change to a screen says which
  journeys it breaks. A journey is for the gallery and check only, as
  transitions are: never handed off.

RESPONSIVE
  tokens.json "breakpoint" splits widths into compact and regular; `render
  --width` picks one. Two tools:
    "only": "regular"                        keep the node at one breakpoint
    "columns": {"compact": ["1fr"], "regular": ["58%", "1fr"]}
                                             any value, one per breakpoint
  A responsive value names both breakpoints; a value the same at both is
  written once.

BUILT-IN COMPONENTS

  Scroll, Stack, List, FieldGroup
                   a column of children. gap, padding, radius, border, elevation
  Card             a column, gap 16 unless gap is given. same frame props

  StickyBar        a row with a line on top, ends pushed apart

  Carousel         a row of 280-wide cards cut at the edge

  Link             text, font (default font.subhead), trailingIcon (adds ›)

                   size ("small"), disabled
  IconButton       icon: a 40 circle
  Glyph            icon, size (default 24), font (a smaller icon), background (an ink)
  Badge            text: a small pill
  Rating           value: "★ 4.9"

  ImageCarousel    each over images (or items), aspectRatio ("4:3"): one photo, "1 / N"

  PriceBreakdown   lines (list of names), total (default "合计")

                   when not given). Drawn at the first of its widths, as
                   tall as that state for the box's width unless aspectRatio

                   description declares the screen, it has no such state, or
                   the state cannot be drawn (it has findings), and refuses

                     { "id": "preview", "component": "Wireframe",

  write what the platform needs to know, such as "minLength", "sticky".
  The built-in components use the fonts font.body, font.subhead, font.caption,
  font.heading and font.price: define them in tokens.json.

DOMAIN.JSON
  The domain a project's screens share, at the project root: the nearest
  directory at or above a screen holding it.
  {
    "types":      { "Order": { "id": "string", "total": "money" } },
    "conditions": { "Order.cancellable": { "when": "status == \"pending\"", … } },
    "operations": { "cancelOrder": { "command": "Cancels an order",
                                     "params": { "id": "string" },
                                     "requires": "Order.cancellable",
                                     "fails": { "notFound": "…" } } },
    "samples":    { "twoJourneys": [ { "name": "Buy", … }, { "name": "Cancel", … } ] }
  }
  "samples" names values fixtures start from with "$sample" (FIXTURES);
  each is any JSON value, untyped here, checked as the field it fills.
  Each key is written as in screen.json (DATA AND TYPES, CONDITIONS,
  OPERATIONS), and nothing else goes there. Every command reads each screen
  of the project as if it declared the domain's itself: a screen uses
  "Order" in its "data" and calls "cancelOrder" by name, and `handoff`, `cli`
  and its golden outputs come out as if it had written them. A screen adds
  its own beside them (one only it uses, such as a type that wraps the
  domain's with view state, "OrderRow": { "order": "Order", "menuOpen": … }),
  but never one of a name
  the domain declares: check names the screen's at "types.Order" (or
  "conditions.…", "operations.…"), says it shadows the domain's, and reads
  the domain's in its place. A finding about the domain's file itself is
  at "domain.json …"; one inside a declaration it holds is at its dotted
  path, as if the screen held it, and is fixed in domain.json.
  A type several screens use goes here once, even one only the screens
  hold: a row type with view state ("OrderRow" above, its "menuOpen"
  marked "view": true) used by two screens is declared in domain.json, not
  copied into each. A screen that declares one the domain holds is named
  as shadowing it: delete the copy, and check, render and the gallery
  read the screen as before.
  A condition the domain shares is declared on a type (CONDITIONS), as
  "Order.cancellable", and each screen reads it through its own values
  of the type. A screen is held only to the ones it reads: one that never
  reads Order.cancellable may have every order pending, and check lists
  only those it reads, with the ones their "when" uses. One that is not on
  a type reads the data of each screen that uses it, so share one only
  when every such screen holds the fields it names; a condition over one
  screen's data stays that screen's.

TOKENS.JSON
  {
    "color":      { "primary": "#3B5BDB", "text": "#222222", "textSecondary": "#6A6A6A",
                    "border": "#DDDDDD", "surface": "#FFFFFF" },
    "space":      { "1": 4, "2": 8, "3": 12, "4": 16, "6": 24 },
    "radius":     { "sm": 8, "md": 12, "pill": 999 },
    "font":       { "body":    { "size": 16, "weight": 400, "lineHeight": 22 },
                    "caption": { "size": 14, "weight": 400, "lineHeight": 18 }, … },
    "elevation":  { "card": { "y": 2, "blur": 8, "color": "#0000001A" } },
    "breakpoint": { "compact": [0, 743], "regular": [744, null] },
    "widths":     [390, 1440]
  }
  "widths" are the widths in points the project's descriptions are drawn
  and checked at, each a whole number from 200 to 4000: check lays every
  state out at each, the gallery draws a state at each side by side, in
  the order named, and `render` draws at the first unless given --width.
  With no "widths", 390 (a phone) and 1120 (a desktop).
  A token is named by its dotted path: "space.4", "radius.md", "font.body",
  "color.textSecondary", "elevation.card". A length is a number or a token
  naming one. Groups and names are the project's; a platform file names
  them in code ("tokenNaming"). The wireframe is gray: color.textSecondary
  draws muted, color.primary strong, color.border as a line, other colours
  as text. Colour itself is out of a design's reach, so the discussion stays
  on structure: no token or ink draws a hue. Where a meaning rides on a
  colour (blue for a journey, orange for a guess), let the wireframe show
  it in structure as well (an icon, a word, a strong fill or a dashed
  line), and say the colour in "$comment" on the node or in the
  component's "doc"; a platform file maps the token to the real colour.

LOOKS
  What a look component (COMPONENTS) is drawn as. A component is never a
  guess: write its whole look; check refuses "assumed" on one (a node may
  still carry one).
    "components": { "Chip": {
        "doc": "A filter as a pill: filled when on.",
        "params": { "selected": "bool = false", "text": "string" },
        "look": { "box": "row", "gap": 6, "padding": [6, 12], "radius": 999,
                  "fill":  { "cases": [ { "if": "selected", "then": "strong" }, { "else": null } ] },
                  "stroke": { "cases": [ { "if": "selected", "then": null }, { "else": "line" } ] },
                  "children": [ { "text": "{text}", "font": "font.caption",
                                  "ink": { "cases": [ { "if": "selected", "then": "paper" },
                                                      { "else": "text" } ] } } ] } } }
  Beside "params", "look" and "doc", a component may say how a platform treats it, which
  `compare` reads (each true or false):
    "scrolls": true    its content scrolls or pages, so what is in it may
                       lie outside its frame (Screen, Scroll, Carousel)
    "pinned":  true    pinned to the screen, out of its siblings' order
                       (StickyBar)
  A node then writes { "id": "chip-direct", "component": "Chip", "text": "Direct",
  "selected": "{filters.direct}" }, or "selected": "{hasDates}", a
  condition of the screen's, which holds where it does. A look's templates
  read the node's props (after the node's own templates are filled), not
  data, and only those its params declare. A prop is a path, a literal or,
  for a bool, a condition's name in braces; typed params hold each to its
  type (COMPONENTS).
  A look is one of:
    {"box": "row"|"column"|"grid" or none, …box keys}    a box
    {"text": "…", …text keys}                            text
    {"component": "Glyph", "icon": "{leadingIcon}", …props}   another component drawn inside
    {"repeat": 3 | "{list}" | ["50%", "35%"], "each": look}
                       repeated; inside: n (from 1), index (from 0), item
    {"cases": [{"if": …, "then": look}, {"else": look}]}
    "$children"        the node's slots: leading, body, trailing, foot, overlays
    [look, …]          each in turn
  Any look may carry "if"; it is left out when that does not hold.
  Box keys:
    gap padding margin   a length (number or token); padding and margin also
                         [v, h] or [top, right, bottom, left]
    width height size    a length or "70%" of the parent; size sets both
    aspect               "4:3" or a number
    grow shrink basis    flex sharing in the parent row or column
    self                 "start": as wide as its content; in a row, centred across
    items                "start" | "center";  justify "center" | "between" | "end"
                         check refuses a word a key does not take
    columns rows span    grid tracks: a count or ["1fr", "1fr"]; span covers cells
                         a track is "2fr", "40%" or a number of points:
                         ["3fr", "1fr", 48]; check refuses anything else
    fill stroke radius dashed   outline and fill in an ink
    cross topLine        a crossed placeholder, a line on top, in an ink
    wireframe            {"screen": "{screen}", "state": "{state}"}: that state
                         of another description drawn in the box (Wireframe)
    dividers             a line between the cells, in an ink (true: line)
    clip                 cut children at this radius (false: never)
    overflowX            "clip": a row that runs off the edge
    pin                  {"x": "end", "y": "end", "inset": 12}: floats over the
                         parent; each axis start | center | end
    backdrop             true, on an overlay: a see-through dark over the node
                         it floats over, and nothing there can be acted on.
                         Only the whole look of a component put in "overlay", or a
                         box with "pin", floats: check refuses it elsewhere
    itemWidth            every child this wide, not shrinking
    frame                true: the node's padding, gap, radius, border and
                         elevation override the look's (containers)
    children             looks inside it
  Text keys: text, font (token or a size number), ink, weight, maxLines,
  align (start|center|end), underline, strike; also self and pin.
  Inks: text, muted, line, fill, strong, paper, or a colour token, drawn in
  the ink it reads as: color.primary strong, color.textSecondary muted,
  color.border line, a colour near white in tokens.json paper, else text.
  None is a hue: say a colour in "$comment" (TOKENS.JSON).
  Look placeholders take filters, left to right: or:v (when missing),
  count, first, last, head, tail (first word / the rest), slashes
  (2026-11-12 → 2026/11/12), glyph (an icon's character), atLeast:n, atMost:n.
    "columns": "{columns|or:2}"     "repeat": "{items|count|atMost:5}"
  A look's "if" uses the condition grammar over props written without
  braces: "value && value != \"\"", "size == \"small\"", "value|first";
  check refuses one that is not the grammar, and a filter that is none.
  A prop holds when given and not false; "" counts as given.
  Any key named icon or ending in Icon holds a Material Symbols name.

A WHOLE SCREEN
  It passes `check`. A condition holds no format and no arithmetic, so a
  list's length is a derived int beside it.
  {
    "screen": "Inbox", "title": "Inbox", "tokens": "tokens.json",
    "data":  { "inbox": "Inbox" },
    "types": { "Inbox": { "count": { "type": "int 0..", "derived": { "app": "messages' length" } },
                          "messages": "Message[]" },
               "Message": { "from": "string 1..", "unread": "bool = false" } },
    "conditions": { "hasMessages": { "when": "inbox.count > 0", "label": "Has mail" } },
    "fixtures": {
      "some":  { "inbox": { "count": 1, "messages": [{ "from": "Ana", "unread": true }] } },
      "empty": { "inbox": { "count": 0, "messages": [] } }
    },
    "root": { "id": "inbox", "component": "Screen", "padding": "space.4", "children": [
      { "id": "empty", "component": "EmptyState", "if": "!hasMessages",
        "icon": "inbox", "title": "No mail" },
      { "id": "list", "component": "List", "if": "hasMessages", "each": "inbox.messages",
        "item": { "id": "msg-{index}", "component": "ListItem", "title": "{item.from}",
                  "leadingIcon": { "cases": [ { "if": "item.unread", "then": "mail.fill" },
                                              { "else": "drafts" } ] },
                  "on": { "tap": { "navigate": "Message", "with": {"index": "{index}"} } } } } ] },
    "phases": { "loading": { "id": "loading", "component": "Screen", "children": [
      { "id": "sk", "component": "Skeleton", "shape": ["line 90%", "line 90%"] } ] } }
  }
